## Objective

Prevent arbitrary authenticated users from reading or writing nonprofit
verification records.

## Evidence reviewed

- `audits/2026-08-daanaa-baseline/16-first-implementation-package.md` (read at `f074cd12d54`)
- `firestore.rules`, `firebase.json`
- `frontend/src/lib/firebase.ts`, frontend Firestore usage (grep)
- `daanaa_api.py` lines ~10978–11132 (`nonprofit_verifications` endpoints)
- `scripts/email_service.py` (Firestore REST usage)

## The defect (confirmed, not assumed)

`firestore.rules:30-33` read:

```
match /nonprofit_verifications/{nonprofit_id}/{document=**} {
  allow read, write: if request.auth.uid != null;
}
```

Any authenticated user could read **and write** every nonprofit's verification
records across the entire wildcard subtree, including verifying an organization
they have no relationship to. The package's evidence claim is accurate.

## Finding that changes the package's stated impact

The package says the fix "restores nonprofit/volunteer data control." That
overstates it, and the record should say so:

- `nonprofit_verifications` in this codebase is a **SQLite table** in
  `daanaa_api.py`, not a Firestore collection. Writes go through
  `POST /api/nonprofit/<ein>/verify/<type>`, gated by `_authorize_claimant()`.
  Reads are a deliberate public projection (`"public, shows badge credibility"`)
  limited to `verified`/`expired` rows.
- **No code in this repository reads or writes a Firestore collection of that
  name.** `frontend/src/lib/firebase.ts` initializes `getAuth` only — never
  `getFirestore` — and there are no Firestore reads/writes in `frontend/src`.
- `firebase.json` does deploy `firestore.rules`, so the permissive rule is live
  regardless of whether our code uses it. Rules govern direct SDK/REST access,
  so any data present in that collection was exposed to every authenticated user.

**Net:** the fix is correct and worth shipping as deny-by-default, but its
security value is defense-in-depth over a collection our code does not use, not
recovery of control over the verification data users actually see. Whether that
Firestore collection holds data cannot be determined from this repository; it
requires production inspection, which was not performed.

## Change made

`firestore.rules` — `nonprofit_verifications` now `allow read, write: if false;`

Denied outright rather than narrowed, because no client legitimately needs
access: all legitimate paths are server-side via the Firebase Admin SDK, which
bypasses rules. This satisfies "unspecified access is denied" without inventing
a role-management system the package explicitly excludes.

## Tests

**Written and passing (static):** `tests/test_firestore_rules_p0_sec_001.py` — 6 tests.
Parses `firestore.rules` and asserts the block denies client access, that the
original `request.auth.uid != null` grant cannot return, that the `{document=**}`
subtree stays covered, and that wallet/audit rules are unchanged (scope guard).

Acceptance criterion "tests fail against the old permissive policy" verified
directly: reverting the single line produces 2 failures; restoring produces 6 passes.

**Written, NOT executed (behavioural):** `tests/firestore_rules/nonprofit_verifications.rules.test.js`
Requires `@firebase/rules-unit-testing` + a Java runtime for the Firebase
emulator. Neither is installed, and adding that toolchain is a dependency
decision that has not been made. **P0-SEC-001 is therefore verified statically
only.** Do not report it as behaviourally verified until these run.
