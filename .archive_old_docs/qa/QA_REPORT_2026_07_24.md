## Priority 1 failures

### P0: Random shuffle is not implemented end to end

The frontend sends `sort=random` and a seed, but the local backend’s `_order_clause()` has no random branch. It falls through to `organization_name ASC`. The frontend’s client shuffle is also gated by `effectiveHiddenGem`, while hidden gems are off by default.

Observed:

```text
sort=organization_name&order=asc → 0 TIENOU TI DIERO BAAFIRI
sort=random&seed=qa-seed-one → ZZYZX FOUNDATION
sort=random&seed=qa-seed-two → ZZYZX FOUNDATION
sort=random&seed=qa-seed-three → ZZYZX FOUNDATION
```

Required correction:

- Decide whether shuffle belongs in the API, frontend, or both.
- If API based, implement deterministic seeded ordering that works across pages and filters.
- If frontend based, fetch a defined candidate pool and shuffle that pool consistently; do not shuffle only the first page and call it fair across the full directory.
- Make the UI state, hidden gem state, URL state, and backend sort contract agree.
- Add automated tests proving two seeds produce different orders and the same seed reproduces the same order.

### P1: Guided discovery location choices are incomplete

In `frontend/src/pages/GuidedDiscovery.tsx`, selecting `A city or ZIP code` or `A specific state` resets the selection to `nationwide` instead of opening an input or selector. Selecting `Near me` sets `near=user-location`, but there is no geolocation permission flow or resolved location passed to the API.

Required correction:

- Add a ZIP/city input and a state selector.
- For `Near me`, request permission only after the user clicks the option, resolve the location, and show the resolved city/state before continuing.
- If location cannot be resolved, explain that clearly and allow nationwide search.
- Add tests for each location path and for a failed location lookup.

### P1: Guided discovery filtering is not aligned with available data

The guided page requests `per_page=100`, then builds a shortlist in the browser. It does not request a random or stable seed, and “Show another list” only reprocesses the same result array. It cannot reliably produce a fresh list when the first API page contains fewer than 25 suitable organizations.

Required correction:

- Define the candidate pool and pagination contract.
- Make `Show another list` select a different deterministic page or candidate window while preserving the same criteria.
- Never label a result as matching a preference unless the API response contains the supporting field.
- Do not use unavailable fields such as volunteer status or recent filing year without verifying their API contract.

## Guided discovery observations

The route exists at `/discover`, the home page links to it, and the frontend build includes the page. The flow has the intended five-step structure, back/start-over actions, URL state, and transparent result headings.

The following are still required before approval:

- Replace the temporary six-item cause list with the approved Daanaa cause taxonomy or clearly label it as an initial set.
- Add focus management after moving between questions.
- Announce progress changes to assistive technology.
- Use Daanaa theme tokens instead of the generic blue/gray treatment where practical.
- Add a visible source or data freshness cue to each result card.
- Add a real network-error state instead of only logging the fetch failure.
- Add unit and component tests for state encoding, mapping, shortlist limits, and result explanations.

## Production smoke check

The read-only `scripts/health_check.sh` run could not reach the public site during this QA window. It reported timeouts for `/`, `/directory`, `/volunteer`, and `/health`. This is a blocker for production certification, but it does not by itself identify whether the cause is the deployment, proxy, tunnel, or network path.

The health script also has a QA tooling defect: its `curl ... || echo 000` pattern can produce `000000`, and the performance check then attempts an integer comparison against a timeout string. Fix the script so timeout and HTTP status are captured separately.

## Recommended order of work

2. Fix guided location selection and API field contracts.
3. Add guided discovery component and mapping tests.
4. Repair the health check script.
5. Re-run local critical path and full regression tests.
6. Re-run production smoke checks after the team confirms the public service is reachable.
7. Obtain founder approval before any deployment or A/B test.
