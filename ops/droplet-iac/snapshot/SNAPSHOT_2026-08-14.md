## Headline findings (ordered by severity)

### 1. LIVE: systemd env-override drop-in silently disables DAANAA_PROD and points DB_PATH at a path with no file — matches the documented "env var drift" incident pattern

`/etc/systemd/system/daanaa-api.service.d/env-override.conf` (mtime Aug 14 05:58,
i.e. **9 hours before this recon**, so this is current, not historical):

```
[Service]
Environment="DAANAA_PROD="
Environment="DB_PATH=/opt/daanaa/data/merit_registry.db"
Environment="FLASK_ENV=production"
```

Two problems:

- `DAANAA_PROD=` is set to an **empty string**. systemd drop-ins fully replace
  a base-unit `Environment=` key of the same name (they don't merge per-key),
  so this overrides the base unit's `DAANAA_PROD=1` with `DAANAA_PROD=` —
  empty, which the app almost certainly treats as falsy. Per
  `CLAUDE.md`: *"DAANAA_PROD env flag: enables HTTPS-only CSP and HSTS
  headers; absent in dev."* If `droplet_api.py` checks this the same way,
  **production is currently running without the HTTPS-only CSP/HSTS headers
  it's supposed to have.**
- `DB_PATH=/opt/daanaa/data/merit_registry.db` — **no file exists at that
  path.** The actual database is at `/opt/daanaa/merit_registry.db` (one
  level up, top-level, not under `data/`). `/opt/daanaa/data/` contains only
  `analytics/`, `backups/`, `claims/`, `precompute/`.

The service is currently up because `droplet_api.py` serves from
`PRECOMPUTE_DIR` (static JSON, per the documented "never SQLite on droplet"
architecture) and apparently doesn't hard-fail on a missing `DB_PATH` — but
if any code path does read `DB_PATH` (a health check, an admin route, a
future feature), it will hit exactly the `unable to open database file`
failure mode described in the incident brief. **This was not introduced by
this task — it predates this recon by ~9 hours** and should be verified
against `droplet_api.py` source and fixed by whoever owns that drop-in.
Flagging, not touching (out of scope / no live changes made).

### 2. Two stale backup unit files reference a precompute version that no longer exists

`/etc/systemd/system/daanaa-api.service.bak-1786549763` sets
`PRECOMPUTE_DIR=/data/precompute/v2`. `/data/precompute/` only contains `v0`
and `v1` — **v2 does not exist on disk.** If anyone (or a script) ever
restores from that `.bak` file by hand, the service will come up pointed at
a nonexistent precompute dir. The other backup
(`.bak-1786559429`) and the live enabled unit both correctly say `v1`. This
is exactly the "which config is authoritative" tribal-knowledge problem the
task describes — two numbered `.bak` files with no changelog explaining why
they exist or which one (if either) is safe to restore from.

### 3. ufw is inactive; gunicorn is directly reachable on 0.0.0.0:8880, bypassing nginx and TLS entirely

`ufw status verbose` → `Status: inactive`. `ss -tlnp` confirms gunicorn binds
**both** `127.0.0.1:5000` (nginx-only, correct) **and** `0.0.0.0:8880` (all
interfaces, plain HTTP, no TLS, no nginx in front). Anyone on the internet
can currently hit `http://107.170.26.8:8880/...` directly, skipping the CSP/
HSTS/gzip/proxy headers nginx would otherwise add — compounding finding #1.
DigitalOcean cloud firewall may or may not be covering this (not visible
from inside the droplet; would need to check the DO dashboard/API). This is
a real, currently-live gap. Not fixed here — ufw rules are included in the
IaC as opt-in (`--enable-firewall`), not auto-applied, because enabling ufw
wrong can lock out SSH.

### 4. SSL config is clean today (no duplicate `ssl_certificate` directive) — but the fix left evidence worth keeping

`sites-available/daanaa` (port 80) and `sites-available/daanaa-ssl` (port
443) are separate files, each enabled once via `sites-enabled/`. Only
`daanaa-ssl` declares `ssl_certificate` / `ssl_certificate_key` — no
duplication today. A `daanaa-ssl.prev` file sits alongside it (Aug 8,
one minute older), consistent with the ".prev before overwriting" pattern
used elsewhere in this repo (`droplet_api.py.prev`, `dist.prev`) — i.e. this
looks like the aftermath of the incident being fixed by hand, correctly,
with a rollback copy kept. Good pattern; nothing to change. The IaC in this
directory pins the current-good version so a future SSL touch has something
to diff against before editing blind.

Certbot is **webroot**-mode (`authenticator = webroot`,
`webroot_path = /var/www/acme`), not the nginx plugin — so certbot never
auto-edits nginx config on renewal (no `# managed by Certbot` markers
present). Renewal is via `certbot.timer` (systemd), not the legacy
`/etc/cron.d/certbot` cron (that cron file explicitly no-ops itself under
systemd — "will NOT be executed if you are running systemd").

### 5. Ownership/permissions oddities (informational, not fixed)

- `/opt/daanaa/data/` is **world-writable** (`drwxrwxrwx`, 777).
- Several files (`daanaa_api.py`, `frontend/dist/`) are owned by **uid 1000**
  with **no matching user in `/etc/passwd`** (`id 1000` → no such user) —
  an orphaned UID, likely left over from an image/snapshot restore or a
  since-deleted provisioning user. Not a security hole by itself, but a
  sign the droplet's user/permission history isn't fully known — worth a
  founder/ops note, not an autonomous fix (permission changes are gated per
  `CLAUDE.md`).
- `/opt/daanaa/daanaa_api.py` also exists on the droplet (534KB, edited very
  recently — Aug 14 22:22) even though `daanaa-api.service` runs
  `droplet_api:app`, not `daanaa_api:app`. Per `CLAUDE.md`,
  `daanaa_api.py` is the canonical *local* dev backend (SQLite, port 5000);
  its presence on the droplet appears to be a stray copy, not something the
  service depends on. Not touched.

### 6. No crontab on the droplet — this is expected, not a gap

`crontab -l` for root/www-data returns empty; `/etc/cron.d/` only has
distro-standard entries (certbot, e2scrub, sysstat), all self-disabled under
systemd except sysstat. No `daanaa`-specific systemd timers either. This
matches the documented architecture (`docs` / `CLAUDE.md`: "Droplet
architecture: Static precompute served ... never SQLite on droplet") — the
heavy pipeline (scoring, precompute generation, FTS rebuild) runs on the
local dev machine and ships finished artifacts to the droplet; the droplet
itself has nothing to cron. Confirmed, not a finding.
