## PHASE 0 — DISCOVERY

### What Daanaa IS (from files only)

- **Daanaa (daanaa.org)** — a civic 501(c)(3) directory built on public IRS BMF, NCCS, and ProPublica 990 data. Indexes ~430K active deductible 501(c)(3) orgs (`frontend/index.html:18`); ~546K scored embeddings (`merit_api.py:99-102`); deductibility filter at `merit_api.py:604`.

- **Two-product surface:** (a) public directory + scoring/tier UI; (b) private "Giving Wallet" + "Giving List" — both **localStorage/sessionStorage only** (`frontend/src/hooks/useWallet.ts:31`, `frontend/src/contexts/GivingListContext.tsx:60`).
- **Two hard invariants** (per STEWARDSHIP.md §2, §8): (1) NEVER touches money, (2) PRIVATE BY DEFAULT.
- **Unknown / not in files:** revenue model is explicitly TBD (`STEWARDSHIP.md:31`); legal entity status (DBA "Daanaa" under EcoMargins LLC) not yet filed.

## PHASE 2 — MULTI-LENS REVIEW

### 1. STRATEGY — Score 4/5

**Architecture serves the mission well.** STEWARDSHIP principles map cleanly onto build choices:

- *Privacy core (§2)* → wallet is localStorage; donor email never sent to server unless letter-flow opt-in (and even that pipeline is not yet wired — see Product §3).
- *Independence (§7)* → no payment processor, no rev-share fields in `registry_enriched`.
- *Evidence-based trust (§3)* → `score_snapshots` table + `scoring_runs` audit log + visible methodology version (`merit_api.py:18`, `:632`).
- *Small-org fairness (§4)* → peer-group percentile is NTEE1 × revenue band (`compute_composite_score.py:67-70`), not absolute rank. Hidden-gem mechanic surfaces `is_hidden_gem` (`merit_api.py:367`).

**Violation #1 — explainability gap.** Two parallel scoring engines exist: the *live* `compute_composite_score.py` (DB-backing, rev×.65 + rsv×.35) and the *unused* `merit_scorer_v3_3.py` (4-ratio program/sustainability/reserve/leverage). Frontend/methodology page may describe one while DB stores the other. STEWARDSHIP §9 ("decisions should be explainable later") implies a single canonical scorer.

**Violation #2 — Wallet UX exceeds backend reality.** `GivingConfirmation.tsx:113-120` promises donors: *"Once they upload your letter, Daanaa emails it to you and stores it in your wallet."* No API endpoint exists for nonprofits to upload acknowledgment letters; no email-out worker exists. This breaks §3 (evidence-based promises) and §10 (AI/system claims must be supportable).

### 5. SEARCH / DATA QUALITY — Score 4/5

**Scoring model** (`scripts/compute_composite_score.py`):

```
composite = 0.65 × revenue_percentile_in_peer_group + 0.35 × reserve_percentile_in_peer_group
peer_group = NTEECC × revenue_band  (subcategory + size band)
fallback = if regional_group_size < 30 → national group
```

- **Strengths:** explicit weights, peer-bounded (small org never compared to Kaiser per STEWARDSHIP §4), regional fallback respects sample-size thresholds, snapshot-versioned, audited via `scoring_runs`.
- **Weaknesses:**
  - `merit_scorer_v3_3.py` (program/sustainability/reserve/leverage @ 30/25/25/20%) is a **completely different model** that ships in scripts but does not feed the DB. Either delete it or document that it is exploratory.
  - `compute_composite_score.py:62` falls back to `total_assets / total_revenue × 12` when `months_of_reserve` is null — this is a *very crude* reserve proxy and double-counts revenue with the rev_pct dimension. Document and consider null-skip instead.
  - Score bands `Blazing/Burning Bright/Steady Flame/Growing/Just Starting` (`merit_scorer_v3_3.py:84-89`) are not the same vocabulary as the tier names `Beacon/Lantern/Flame/Ember/Spark` (`frontend/src/contexts/GivingListContext.tsx:7`). Two parallel vocabularies for two scoring concepts is fine but should be explained in the methodology page.

**Search:** RRF fusion with `k=60` (`merit_api.py:1129`) and 100 candidates per path is textbook — solid implementation. FTS sanitizer at `_sanitize_fts_query` (`:64-72`) strips FTS5 metacharacters and prefix-matches. Embedding service is local (Vulkan/llama-server primary, Ollama fallback) — privacy-aligned.

**Name cleaning / dedup:** `scripts/clean_names.py` is **corrupted** — file contents are an Aliyun S3 "NoSuchBucket" XML error. Probably a download that got piped wrong. **P1** to either restore or delete. `scripts/merit_dedupe_audit.py` + `merit_dedupe_audit_v2.py` exist but I have not run them; assume duplicate EIN detection has been done.

**Deductibility filter** (`merit_api.py:604`): only `subsection='3' AND deductibility != '2'` — correct for excluding non-deductible orgs. Null-subsection orgs are excluded. The filter is applied to `/api/organizations` and `/api/stats` and the fused-search final fetch, **but not** to `/api/organizations/:ein` (detail). Means: someone with a direct EIN URL can view a non-deductible org's detail page. Mostly acceptable (transparency), but for tier display this can produce a Glow/Spark tier on an org that the directory itself would hide. **P2** to align.

### 7. DEEP SECURITY

#### CRITICAL
- None found.

#### HIGH
- **H1. Admin key compared with non-constant-time `==`** (`merit_api.py:220`). `provided != _ADMIN_KEY` is vulnerable to timing attacks against the admin endpoints (`/api/admin/waitlist/*`, `/api/scoring-runs`). Use `hmac.compare_digest`. Effort: 1-line fix. **P1**.
- **H2. `org_claims` table referenced but not initialized in code** (`merit_api.py:856-988`). A fresh deploy without the manual schema will 500 on `/api/claim/start`. **P0**.
- **H3. Claim PINs logged in plaintext** (`scripts/send_claim_letter.py:138-148` + `:86`). The `verify_url` includes `?pin=XXXXXX` and the JSON entry includes `pin: "XXXXXX"` separately. Anyone with read access to `logs/` can take over an unclaimed org by viewing the log and submitting the PIN. Mitigation: hash the PIN in the log, redact the URL, and chmod `logs/claim_letters.log` to 600. **P0**.
- **H4. Tests reference dead port + dead brand** (`tests/merit.spec.js:3, 7`). Not security per se but a CI green-build is impossible. **P1**.

#### MEDIUM
- **M1. No `Content-Security-Policy` header** (`merit_api.py:276-281` only sets X-Content-Type-Options, X-Frame-Options, Referrer-Policy). The SPA loads no third-party scripts today, but a strict CSP `default-src 'self'; img-src 'self' data:` would harden against future XSS regressions, especially given claimed `custom_mission`/`custom_description` fields land in the DB (`merit_api.py:961-983`) and get rendered. React escapes by default but CSP is defense-in-depth. **P1**.
- **M2. No HSTS header.** Cloudflare will likely add this at the edge once HTTPS is wired, but `set_security_headers` should set `Strict-Transport-Security: max-age=63072000; includeSubDomains` for non-localhost. **P2**.
- **M3. `MAX_CONTENT_LENGTH = 64 KB`** (`merit_api.py:274`) is good for JSON endpoints, but means any future file upload (e.g., letter PDFs from nonprofits) will need explicit raising. Document. **P2**.
- **M4. `secrets.randbelow(900000) + 100000`** (`merit_api.py:863) is fine entropy for a 6-digit PIN but combined with H3 (logged plaintext) the practical entropy is zero against an attacker with log access.
- **M5. `/api/search/semantic`, `/api/search`, `/api/organizations/:ein/similar`** all call out to `_embed_query` which POSTs to `http://127.0.0.1:11436/v1/embeddings` (`merit_api.py:151`) and falls back to `http://localhost:11434/api/embed`. Hardcoded to localhost — no SSRF risk. **OK.**
- **M6. CORS `supports_credentials=False`** (`merit_api.py:200`). Good — donors cannot be CSRF-attacked through the wallet (which doesn't talk to the API anyway). But `_ALLOWED_ORIGINS` includes `http://100.74.118.100:3000` etc. — these are Tailscale IPs and fine for dev. Verify before production that the production deploy strips dev origins. **P2**.
- **M7. No input rate-limit on the search endpoints by query content.** `_sanitize_fts_query` is robust, but the embedding service receives `text=q` directly — an attacker could spam expensive embedding calls. flask-limiter caps `/api/search` at 60/min/IP, `/api/search/semantic` at 30/min/IP. Tolerable, but a 200-char query × 60/min × N IPs could DoS the local llama-server. Consider a token-bucket on embedding service load, or cap `q` length. **P2**.
- **M8. SQL injection — clean.** All endpoints use parameterized queries. `_TIER_HIERARCHY` placeholders (`merit_api.py:382-384`), `_DEDUCTIBILITY_FILTER` is a constant string (`:604`), `cause` filter uses `json_each` with a parameterized `LIKE` (`:374-376`), `sort_by`/`order` are allowlisted (`:386-390`). **PASS.**

#### LOW
- **L1. `.env` committed in `.gitignore` correctly** (`.gitignore:32`). `nonprofit-explorer/.env` is a separate legacy app and contains placeholder values — not Daanaa secrets. Safe.
- **L2. `merit-platform/apps/api/.env.example` is the only `.env*` file tracked by git** (per `git ls-files`). Good.
- **L3. `nohup.out`, `app.log`, `server.log`, `tunnel.log` at repo root.** `.gitignore` excludes `*.log` but `nohup.out` is matched separately (line 23) — confirmed gitignored. Cleanup recommended.
